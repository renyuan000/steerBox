# steerBox 架构设计问题清单

## 文档用途

本文件用于把 `steerBox` 后续架构设计中需要优先回答的问题整理出来，方便逐项讨论、逐项收敛。

本文件不是最终架构方案，也不代表这些问题已经得到结论。

建议把它与 [ARCHITECTURE_DIRECTION.md](./ARCHITECTURE_DIRECTION.md) 配合使用：

- `ARCHITECTURE_DIRECTION.md` 说明当前已经确认的方向
- 本文件聚焦后续仍需设计与决策的问题

## 0. 状态语义与当前结论

状态含义：

| 状态 | 含义 |
|---|---|
| `open` | 尚未形成足够的设计结论，不能作为实现前提 |
| `partially_resolved` | 已有边界或 Phase 1 契约，但仍缺少完整 runtime、跨场景或安全决策 |
| `resolved` | 设计、约束和验证入口已形成稳定结论；不等于代码已实现 |
| `superseded` | 已被新的设计或契约替代，保留仅用于历史追溯 |

截至本轮文档同步，当前状态如下：

| 主题 | 当前状态 | 依据与边界 |
|---|---|---|
| 核心边界 | `partially_resolved` | Phase 1 固定为 shared harness core + software development agent vertical slice；安全智能体仍是后续主线 |
| 长时运行 | `partially_resolved` | Goal / Loop、EventLog、StateStore、checkpoint 有设计；生产级恢复和调度仍待实现 |
| Steering / PolicyGate | `partially_resolved` | 有人类模式、策略门和审计边界；完整策略评估与权限模型仍待收敛 |
| 人在环 | `partially_resolved` | 已定义观察、审批、暂停、恢复和接管模式；控制面交互仍未实现 |
| 审计 / tracing / 回放 | `partially_resolved` | EventLog 是执行事实源，Trace / StateStore / BoardProjection 可重建；完整回放工具仍待实现 |
| Portfolio / Board | `partially_resolved` | Phase 1 固定 schema 和只读 projection fixture；真实多项目并行调度不在 Phase 1 |
| 多模型 | `partially_resolved` | 已有静态 profile、规则路由、prompt pack 和 fallback 契约；adapter 运行时和供应商差异仍待独立收敛 |
| 自进化 | `partially_resolved` | 已有 SystemEvolutionTask 和 local → project → portfolio → global 晋升边界；验证、审批和回滚 runtime 仍待实现 |
| 安全模型 | `open` | 需要单独形成 threat model、trust boundary、secret 和高风险动作策略 |
| 语言和构建 | `open` | 先按模块职责和验证结果选型，当前不把语言选择写死 |

### Phase 1 收敛边界

Phase 1 只验证：

```text
shared harness core
  + software development agent vertical slice
  + one Portfolio / one Project / local sequential fixture
  + Task / TaskRun / Attempt schema
  + EventLog -> StateStore -> BoardProjection read-only fixture
```

Portfolio、Task、Attempt 和 BoardProjection 在 Phase 1 进入 schema、事件和只读 fixture；真实多项目并行调度、workspace/worktree lease、分布式 worker、交互式 TUI/Web control plane 和 self-evolution runtime 不得被写成已实现能力。

## 1. 核心边界

首先要回答的不是“做多少功能”，而是 `steerBox` 最小要解决什么问题。

优先问题：

- `steerBox` 的最小通用核心是什么
- 哪些能力必须同时服务开发智能体和安全智能体
- 哪些能力不应放在核心层，而应留在领域层
- 项目的第一阶段，是先验证通用 harness，还是先验证某一条主线

当前已知方向：

- 项目保持一个统一核心
- 项目承载两条主线：软件开发智能体、安全智能体
- 核心目标是组合长时执行、约束控制、反馈闭环、人在环、审计和 tracing

## 2. 长时运行模型

`steerBox` 不是只做一次性任务式 agent，因此必须尽早定义长时运行模型。

优先问题：

- 长时任务的最小状态机是什么
- 一个任务是否应有 `created / queued / running / waiting / paused / resumed / failed / completed / terminated` 一类状态
- 哪些状态是系统内部状态，哪些状态需要对用户可见
- 任务在重启后如何恢复
- 长时任务如何处理中断、超时、人工暂停和人工接管
- 长任务的上下文、记忆和执行痕迹如何持久化

设计关注点：

- 不应把长时任务仅仅视作一次 prompt 的延长版
- 应显式设计状态延续与恢复机制

## 3. Steering 与跑偏控制

当前项目的一个核心动机，是降低智能体在长任务中的跑偏风险。

优先问题：

- steering 的配置入口是什么
- steering 是通过规则文件、策略对象、任务约束、运行时拦截，还是它们的组合来表达
- 哪类约束是静态约束，哪类约束是动态约束
- 约束违例时，是阻断、降级、请求审批，还是仅记录
- 如何区分“允许尝试”和“禁止执行”
- 如何让 steering 在长时运行中持续生效，而不是只在任务开始时生效

设计关注点：

- steering 必须是长期有效的执行约束，而不是一次性说明
- 约束机制应直接服务于“减少跑偏”和“降低误操作”

## 4. 工具调用与权限控制

无论是开发还是安全方向，都离不开工具调用与环境访问，因此必须尽早定义权限边界。

优先问题：

- tool call 的最小抽象是什么
- 文件读、文件写、命令执行、网络访问、外部服务访问是否应分级管理
- 哪些能力默认允许，哪些能力默认需要审批
- 权限是按工具划分，还是按动作风险级别划分
- 是否需要会话级、任务级、步骤级三层权限
- 命令执行、文件改写、自动响应等高风险动作的审批条件如何定义

设计关注点：

- 权限模型必须可解释
- 工具能力不应默认无限开放
- 约束和权限边界要能被审计

## 5. 人在环与接管模型

项目已经明确要求用户可以随时介入、把控、审查和接管。

优先问题：

- 人在环的最小介入点是什么
- 用户可以在哪些节点审批、驳回、修改约束、暂停或接管
- 人工接管是一次性 override，还是会改变后续策略
- 用户介入后，任务上下文如何延续
- 前台或控制面最小需要展示哪些信息，才能让用户有效决策
- 何种情况必须强制进入人工确认流程

设计关注点：

- 人在环不应只是“出事后再看”
- 设计上应支持主动观察与中途介入

## 6. 审计、Tracing 与回放

项目已经明确要求行为可审计，决策与执行流程可审计、可 tracing。

优先问题：

- 哪些事件必须被记录
- 记录粒度是按任务、按步骤、按工具调用，还是按决策节点
- 是否需要区分审计日志、执行日志和调试 tracing
- 决策依据如何记录
- 工具调用前后的输入输出如何保留
- 修改行为、审批行为、自动响应行为如何回放
- 安全方向中，哪些日志属于敏感数据，如何做脱敏或分级访问

设计关注点：

- 审计与 tracing 不是事后补丁，而应是核心能力
- 必须同时考虑“可追踪”和“不过度泄露敏感信息”

## 7. 反馈闭环与验证机制

项目明确强调反馈闭环，因此必须设计“怎么知道 agent 在收敛”。

优先问题：

- 不同主线的反馈源分别是什么
- 开发方向是否以测试、lint、review、diff 检查作为主要反馈
- 安全方向是否以规则匹配、告警验证、事件归并、处置结果作为主要反馈
- 失败、偏离、未完成如何判定
- agent 收到负反馈后，是重试、回退、换策略，还是升级给人工
- 如何验证“任务完成”不是自我宣称，而是有证据支持

设计关注点：

- 必须显式区分“执行了动作”和“验证了结果”
- 不同领域的闭环机制应复用框架思路，但不强行统一细节

## 8. 软件开发方向的专用问题

开发智能体方向后续至少需要回答以下问题：

- 代码修改范围如何约束
- 是否需要内建任务拆解与阶段性提交机制
- 测试、构建、lint、review 的调用时机如何定义
- 出现失败后，是自动修复、自动回退，还是请求人工确认
- 如何降低对无关文件的误修改
- 如何定义“长时间自动化开发”的阶段边界与收敛条件

设计关注点：

- 重点不是“会生成代码”
- 重点是“能在受控约束和验证反馈下长期推进开发任务”

## 9. 安全方向的专用问题

安全智能体方向后续至少需要回答以下问题：

- 安全日志与信号的输入模型是什么
- 任务是流式持续分析，还是按窗口/批次分析
- 事件发现、分析结论、响应建议和响应执行如何分层
- 什么动作只能建议，什么动作可以自动执行
- 自动化响应是否必须经过审批
- 如何避免安全方向的自动化能力越权、误报或误处置
- 如何支持持续运行中的观察、干预和接管

设计关注点：

- 当前优先落点更接近持续工作的安全运维智能体
- 自动化不能脱离安全边界与审批模型单独讨论

## 10. 通用层与领域层的接口问题

一个项目承载两条主线，最终成败很大程度上取决于接口边界是否清楚。

优先问题：

- 通用层向领域层暴露的最小接口是什么
- 领域层如何注册自己的工具、规则、状态和反馈源
- tracing、审计、审批、恢复等能力是否由通用层统一提供
- 领域层是否只能扩展，不应反向污染通用层
- 如何避免为某一条主线定制过多逻辑，导致“通用层”名存实亡

设计关注点：

- 先定义接口，再谈目录
- 先定义职责，再谈语言

## 11. 语言与实现分工问题

当前考虑过 Rust、Python、C、Go，但尚未定稿。

优先问题：

- 哪些模块需要优先保证稳定性、性能或长期运行能力
- 哪些模块更适合快速试验与迭代
- 哪些模块必须尽量减少运行时复杂度
- 哪些模块需要与底层系统或现有工具深度交互
- 语言选择是按运行职责划分，还是按团队/个人开发效率划分

设计关注点：

- 不要先定语言，再硬塞职责
- 更合理的顺序是先定模块职责，再选实现语言

## 12. 第一阶段原型的收敛问题

方向明确后，还需要回答“第一阶段最小原型到底做什么”。

优先问题：

- 第一阶段是先做通用 harness 原型，还是先做一个开发方向或安全方向的垂直切片
- 第一阶段必须具备哪些最小能力
- 哪些能力可以先用简化版证明方向可行
- 什么算作第一阶段验证成功
- 什么信号说明当前方向需要收缩，而不是继续堆功能

设计关注点：

- 第一阶段目标应该是验证核心假设
- 不应在还没验证最小通用核心时，过早铺开所有场景

## 建议的讨论顺序

为了避免同时展开过多问题，建议后续按这个顺序讨论：

1. 核心边界
2. 长时运行模型
3. Steering 与权限控制
4. 人在环介入点
5. 审计、tracing 与回放
6. 反馈闭环与验证机制
7. 通用层与领域层接口
8. 第一阶段原型范围
9. 语言与实现分工

## 当前使用方式

后续如果要继续架构讨论，可以直接从本文件中选一个章节逐项收敛。

更合适的节奏是：

- 每次只讨论一个主题
- 对已达成一致的问题形成明确结论
- 对仍然开放的问题保持开放状态，不提前写死

这样可以避免在目录、语言、模块划分上过早做出无法验证的承诺。
