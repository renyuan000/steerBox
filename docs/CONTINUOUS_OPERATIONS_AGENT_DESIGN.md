# 持续运维智能体设计

## 文档定位

持续运维智能体面向普通 IT 运维、SRE、AIOps 和混合云资源治理。它的目标是稳定性、可用性、性能、容量、成本和恢复效率，不把安全事件与稳定性故障混成同一种领域模型。

本文是领域设计方向，不代表能力已实现；第一阶段只保留接口和边界。

## 运行形态

- 周期巡检：按服务、资产、指标或资源范围定期运行；
- 事件触发：由指标异常、部署变化、资源申请、工单或用户消息触发；
- 故障协同：围绕一个 `OperationsIncident` 持续调查、分派、验证和恢复；
- 常驻观察：后台维护服务健康、容量、成本和变更状态；
- 交互接入：用户通过聊天查询当前状态、补充上下文、审批或接管。

## 核心领域对象

| 对象 | 作用 |
|---|---|
| `Service` / `Asset` | 服务、主机、集群、云资源和依赖关系 |
| `HealthSignal` | 指标、日志摘要、探活、变更和巡检结果 |
| `OperationsIncident` | 稳定性或可用性问题的生命周期 |
| `ChangeRecord` | 部署、配置、扩缩容和资源变更 |
| `Runbook` | 可版本化、可审批、可验证的操作流程 |
| `CapacityObservation` | 容量、性能、利用率和趋势分析 |
| `CostObservation` | 成本、预算、利用率和优化机会 |
| `RecoveryAction` | 恢复、回退、隔离或人工接管动作 |
| `VerificationResult` | 动作后健康、可用性和回退效果验证 |

这些对象与共享 `Task / TaskRun / Attempt / Evidence` 关联，但不替代共享任务模型。

## 运行闭环

```text
服务/资源/变更信号
  -> 上下文、依赖和影响范围确认
  -> 健康评估或故障假设
  -> 只读诊断与证据收集
  -> 生成建议或受控恢复任务
  -> PolicyGate / 审批 / 执行
  -> 恢复后验证
  -> 关闭、升级、复盘和知识沉淀
```

默认先诊断再执行。资源压降、扩缩容、配置变更和发布操作必须记录预期收益、影响范围、回退方式、不可恢复副作用和验证标准。

## 客户需求映射

客户提供的混合云需求主要映射到本方向：智能巡检、健康评估、跨团队协同、存量资源分析与压降、新增资源申请评估、自然语言问数。客户材料没有冻结数据源、接口、权限、自动执行范围或量化指标，因此这些内容必须保持待确认状态。

自然语言转 SQL 首期应限定为：只读、数据源白名单、表/字段权限、租户范围、查询成本限制、结果脱敏、SQL 和结果可解释、失败可复核。不得让生成 SQL 直接获得写权限。

## 长期运行与人机协同

后台任务必须由共享 Durable Long-Running Agent Runtime 托管，拥有心跳、租约、预算、超时、暂停、恢复和归档。用户接入聊天时，应读取任务状态和证据，而不是重新创建一个失去上下文的新任务。

风险分级建议：

- 低风险：只读巡检、报告生成、通知和趋势计算，可按策略无人值守；
- 中风险：生成变更计划、资源优化建议和待审批工单；
- 高风险：生产变更、资源删除、网络策略变化和不可逆操作，必须人工审批或接管。

## 非目标

- 不把持续运维智能体设计成安全运营智能体的替代品；
- 不在 Phase 1 实现真实云厂商写操作或生产自动恢复；
- 不把客户外部材料中的目标、指标和接口写成已确认规格；
- 不允许模型直接绕过身份、权限、审批和回退边界。
