# 客户需求参考：混合云运维与成本优化

## 文档定位

本文件整理客户提供的项目截图和文字材料，作为 `steerBox` 进行领域分析、场景建模和后续需求追溯的外部参考。

它不是 `steerBox` 的总需求，也不是当前 Phase 1 的实现范围。客户材料来自外部架构输入，主要对应本项目的持续运维方向及其相关运维领域应用；其中安全协同内容可作为安全运营方向的外部场景输入，但不改变软件开发 Phase 1 的方向和边界。

本文件区分三类内容：

- **客户明确提出**：能够直接从客户材料追溯的项目目标、痛点和能力。
- **整理抽象**：为了便于讨论，把客户材料归纳成的业务流程或能力分层，不等于客户已经确认的技术规格。
- **待确认**：客户材料没有给出、不能由本项目自行补写的指标、接口、权限和实施边界。

## 1. 客户项目概览

客户材料对应的项目标题为：

> 中国 XX2026 年基于多智能体技术的混合云运维与成本优化场景应用研发项目

材料列出四个子课题：

| 子课题 | 客户材料中的主题 | 整理后的业务重点 |
|---|---|---|
| 子课题 1 | 应急指挥决策中枢与智能巡检场景应用能力研究 | 运维协同、主动感知、多智能体调度、健康评估和巡检 |
| 子课题 2 | 服务器资源利用率智能分析与压降策略生成研究 | 存量资源分析、压降策略和成本优化 |
| 子课题 3 | 服务器资源申请必要性、合理性的智能评估能力研究 | 新增资源申请的必要性、合理性和申请管控 |
| 子课题 4 | 云资源信息智能问数能力研究 | 混合云资源信息的自然语言查询和分析 |

从客户材料看，子课题 1 偏向运维协同和应急决策，子课题 2～4 偏向混合云资源管理。四个子课题是否由一个统一产品承载，客户材料尚未明确。

## 2. 与 steerBox 四个专业方向的关系

`steerBox` 当前采用四个专业研发方向；客户材料主要落在持续运维方向，并与安全运营方向存在部分场景交集：

1. **软件开发智能体**：面向软件开发、代码修改、测试、审查、验证和受控开发工作流。
2. **持续运维智能体**：面向服务稳定性、巡检、资源、容量、性能、成本和故障恢复。
3. **安全评估与漏洞研究智能体**：面向授权安全审计、漏洞研究、PoC 模拟验证和修复复测。
4. **安全运营智能体**：面向持续安全信号分析、事件调查、受控响应和防护效果验证。

客户材料与本项目的关系应按下表理解：

| 客户需求 | 主要归属 | 对软件开发智能体的关系 | 对持续运维/安全运营智能体的关系 |
|---|---|---|---|
| 应急指挥决策中枢 | 持续运维及相关运维领域应用 | 仅复用通用 harness、任务、验证和审计能力 | 直接相关，属于运维协同与决策场景 |
| 智能巡检和健康评估 | 持续运维及相关运维领域应用 | 不属于编码智能体业务目标 | 直接相关，需接入监控、巡检和事件数据 |
| 多智能体运维协同 | 持续运维及相关运维领域应用 | 复用通用编排和人机协同机制 | 直接相关，需定义运维领域角色和工具 |
| 资源利用率分析与压降 | 混合云资源管理领域应用 | 不属于编码智能体业务目标 | 直接相关，但需要独立的资源、成本和执行模型 |
| 新增资源申请评估 | 混合云资源管理领域应用 | 不属于编码智能体业务目标 | 直接相关，需要审批、预算和策略边界 |
| 自然语言转 SQL 问数 | 混合云资源管理领域应用 | 不属于编码智能体业务目标 | 可作为只读查询领域能力接入 |
| 过程知识沉淀、审计和人工介入 | 通用 harness 能力 | 编码任务和运维任务都可复用 | 编码任务和运维任务都可复用 |

**边界结论：**客户材料可以作为持续运维及相关安全协同方向的真实外部场景输入，但不能反向定义 `steerBox` 的全部产品方向，也不能把混合云资源管理能力写成软件开发智能体的 Phase 1 交付内容。

## 3. 客户明确提出的总体目标

客户希望构建一个基于“主动感知、智能协同、知识自驱”理念的下一代智能运维中枢。

客户明确希望该中枢不再只是被动工具集合，而能够：

- 主动“倾听”运维团队沟通；
- 理解沟通上下文和运维背景；
- 智能调度多个智能体协同工作；
- 将处理过程自动沉淀为结构化知识；
- 将主动感知、智能协同和系统健康评估结合起来；
- 将运维模式从“人找事”的被动响应，转向“事找人”的主动预防和智能决策。

客户材料指向的业务价值包括：

- 提升跨团队故障协同效率；
- 减少运维知识流失和重复劳动；
- 提升人机协作效率；
- 加强运维流程合规和风险控制；
- 提升 IT 系统稳定性、可靠性和运维智能化水平。

## 4. 子课题 1：应急指挥决策中枢与智能巡检

### 4.1 客户提出的痛点

- 跨团队故障协同存在效率瓶颈；
- 运维知识流失，重复劳动较多；
- 人机协作效率不足；
- 运维流程合规和风险控制需要加强；
- 传统运维偏向“人找事”，缺少主动预防和主动决策。

### 4.2 客户需要的能力

| 能力方向 | 客户需求含义 |
|---|---|
| 主动感知 | 主动获取运维沟通、系统状态和巡检信号，并理解上下文 |
| 智能协同 | 按故障或运维任务调度多个智能体协同分析、执行和反馈 |
| 应急指挥 | 支持任务分派、跨团队协作、进度跟踪和决策辅助 |
| 智能巡检 | 支持系统健康状态识别、异常发现和巡检结果分析 |
| 知识自驱 | 将处理过程、经验和结果沉淀为结构化知识 |
| 合规与风险控制 | 对运维流程、智能体动作和人机协作过程进行约束、审计和风险控制 |
| 主动预防 | 从事后响应逐步转向提前发现问题并通知相关人员 |

### 4.3 整理抽象的业务闭环

以下流程是对客户材料的整理抽象，尚未构成客户确认的接口或实现规格：

```text
运维沟通 / 系统状态 / 巡检信号
  -> 上下文理解与问题识别
  -> 应急任务或巡检任务生成
  -> 多智能体协同调度
  -> 分析、执行、验证与人工介入
  -> 过程、结果和经验结构化沉淀
  -> 主动通知、预防建议或后续任务
```

## 5. 子课题 2～4：混合云资源智能优化与问数

### 5.1 客户明确提出的共性痛点

- 存量资源依靠人工分析，资源压降效率低；
- 新增资源申请缺少管控，存在盲目申请；
- IT 运维协同与响应滞后；
- 体系化流程和平台化智能能力不足；
- 资源浪费、成本高企和查询效率低。

### 5.2 三个创新方向

| 方向 | 客户需要解决的问题 | 客户期望的结果 |
|---|---|---|
| 存量资源智能分析与压降 | 识别利用率不足、配置不合理或可优化的存量资源 | 生成压降策略，减少资源浪费和成本 |
| 新增资源多维度评估 | 判断资源申请是否必要、合理，是否存在替代或优化方案 | 在申请源头增加智能评估和管控 |
| 自然语言转 SQL 智能问数 | 降低人工编写查询和跨系统获取资源信息的成本 | 通过自然语言查询混合云资源信息，提高查询效率 |

### 5.3 整理抽象的业务闭环

```text
混合云资源数据 / 资源申请 / 自然语言问题
  -> 数据理解、权限校验和上下文补全
  -> 资源利用率分析、申请评估或 SQL 生成
  -> 查询结果、压降建议或申请决策辅助
  -> 结果验证、解释和人工确认
  -> 资源调整、申请流程推进或知识沉淀
```

其中“资源调整”和“申请流程推进”是否允许系统自动执行，客户材料没有说明，必须经过权限、安全和流程评审后确认。

## 7. 对 steerBox 的设计映射

本节是 `steerBox` 内部分析，不是客户承诺，也不代表相关能力已实现。

| 客户能力 | 可复用的通用 harness 位置 | 需要新增的运维/资源领域能力 | 当前状态 |
|---|---|---|---|
| 多智能体协同调度 | `Portfolio / Task / TaskRun / Attempt / BoardProjection` | 运维角色、交接、冲突和资源工具 | 通用对象已在 Phase 1 契约中锁定；领域 runtime 未实现 |
| 主动感知与长时运行 | `EventLog / StateStore / LoopController / GoalAlignment` | 事件接入、信号关联、告警和巡检触发器 | 有通用设计；运维接入未定义 |
| 过程知识沉淀 | `EventLog / TraceStore / Evidence / Memory` | 运维知识分类、检索和审批晋升 | 有通用边界；运维知识模型未定义 |
| 健康评估与智能巡检 | `Verification / Evaluation / Task` | 指标、规则、巡检模板和领域评估器 | 未实现 |
| 资源利用率分析与压降 | `Task / PolicyGate / SideEffectLedger` | 资源、成本、利用率、收益和回退模型 | 未定义 |
| 新增资源申请评估 | `Task / Verification / Human Steering` | 申请、预算、容量、审批和替代方案模型 | 未定义 |
| 自然语言转 SQL 问数 | `ToolRegistry / Model Adapter / PolicyGate` | 数据源、SQL 方言、只读权限、结果解释 | 未定义 |

明确边界：`steerBox` 可以承接这些场景所需要的通用 harness、任务编排、审计和人机协同设计；它当前不是混合云资源管理产品，也不是已经交付的应急指挥系统。

## 8. 待客户确认的问题

### 8.1 平台和用户范围

- 子课题 1 与子课题 2～4 是否由同一平台承载？
- 主要用户是运维工程师、资源管理员、审批人员、管理人员，还是其他角色？
- 哪些团队需要跨团队协同，责任边界如何定义？
- 系统面向单一组织、多个业务系统，还是多个云租户？

### 8.2 数据和系统接入

- 混合云包含哪些云厂商、私有云平台和资源类型？
- 资源利用率、账单、监控、CMDB、工单、IM/会议沟通和巡检数据来自哪里？
- 是否已有统一资产、资源、成本、工单和身份权限数据模型？
- 数据更新频率、历史保留时间和跨系统关联键是什么？
- 运维沟通内容是否允许进入模型上下文，哪些内容必须脱敏或禁止处理？

### 8.3 压降和申请评估

- “压降”包括规格调整、关停、释放、迁移、配额回收，还是只生成建议？
- 利用率使用哪些指标和时间窗口，如何处理高峰、季节性和异常数据？
- 压降收益、风险和回退方案如何计算？
- 哪些资源类别必须人工审批？
- 新增资源申请的评分维度、审批门槛和所需证据是什么？
- 评估结果是建议、补充材料、驳回，还是进入人工审批？

### 8.4 智能问数和安全边界

- 允许查询哪些数据表、字段和时间范围？
- 使用哪种 SQL 方言，是否需要跨数据源查询？
- 是否只允许只读 SQL，是否需要行级、列级和租户级权限？
- 查询结果是否需要脱敏、汇总、解释、导出或二次分析？
- SQL 生成失败、结果为空或结果不可信时如何处理？
- 哪些多智能体动作允许无人值守，哪些必须人工确认？

### 8.5 量化验收指标

客户材料没有给出量化指标，至少还需确认：

- 故障发现、研判、协同和响应时延目标；
- 巡检覆盖率、异常识别率和误报/漏报容忍度；
- 资源压降金额、资源利用率提升或成本节省目标；
- 新增资源申请评估准确性、人工审核减少量和拦截目标；
- 自然语言问数成功率、SQL 正确率、查询时延和数据权限违规率；
- 知识复用率、重复劳动减少量和人工介入比例；
- 可用性、审计留痕完整性、回退时间和安全事件容忍度。

## 9. 当前结论

截至本文件整理时，可以确认：

- 客户真实需求是“智能运维中枢 + 混合云资源优化与问数应用”，不是单一聊天机器人；
- 子课题 1 主要对应持续运维方向，并与安全运营方向存在部分场景交集；
- 子课题 2～4 主要对应混合云资源管理这一运维领域应用；
- 编码智能体不承接上述云资源业务目标，但可以复用通用 harness 的任务、验证、审计和人机协同能力；
- 客户材料尚不足以冻结数据模型、接口协议、自动执行权限和量化验收指标；
- `steerBox` 需要保持“共享 harness + 四个专业方向 + 领域 adapter”的分层，不能把客户场景直接改写成项目总方向。

下一步应先向客户确认范围、数据、权限、指标和自动化边界，再把确认后的运维场景拆成领域 adapter、控制面查询和可验证任务；不应因为这份外部需求材料而扩大编码智能体 Phase 1。
