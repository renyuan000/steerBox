# steerBox 架构方向总结

## 文档目的

本文件用于沉淀当前已经明确的项目定位、问题定义和架构方向，作为后续 README、架构设计、目录规划与原型实现的上位指导。

本文件不是最终实现规格，也不代表当前仓库已经具备对应能力。

## 当前项目定位

- `steerBox` 当前首先是一个 `learning-first` 的 Harness Engineering 学习项目。
- 现阶段重点不是立即做成通用平台，而是通过具体智能体场景，学习如何设计、约束、观测和优化 agent harness。
- 后续如果项目逐步成熟、形成稳定能力，再考虑向更通用、更可实用的框架演进。

## 核心问题

`steerBox` 关注的核心问题不是“让 agent 会不会做事”，而是如何把以下能力稳定组合成一个可持续运行的 harness：

- 长时执行
- 约束控制
- 反馈闭环
- 支持人在环、无人值守、被动观察、主动审批与人工接管
- 行为可审计
- 决策与执行流程可追踪

换句话说，项目的核心目标是：在安全、可控、可引导的环境中，让智能体能够长期执行任务、持续接收反馈、减少跑偏，并根据任务风险和运行模式支持无人值守、被动观察、主动审批、人工介入和接管。

## 总体项目策略

- 当前保持为一个项目，而不是拆成多个独立学习项目。
- 在一个项目内承载四个专业研发方向：
  - 软件开发智能体
  - 持续运维智能体
  - 安全评估与漏洞研究智能体
  - 安全运营智能体
- 四个方向统一使用共享 Harness 和控制面，但领域模型、授权契约、工具集和高风险动作边界必须分离。
- 后续在代码与目录设计上，应优先区分“通用底座”和“领域专用能力”，避免过早混合、相互污染。

这意味着项目层面是一个，产品展示可以归纳为“工程智能体”和“安全智能体”两个产品族，但研发架构采用四个独立方向。

## 主线一：软件开发智能体

软件开发方向当前关注：

- 长时间自动化开发
- 代码管理
- 测试执行
- 重构
- 开发工作流控制
- 持续反馈与持续修正

这一方向要解决的问题，不只是“让 agent 会写代码”，而是：

- 让 agent 能够在较长任务链条中持续推进
- 让 agent 在文件、命令、修改范围等方面保持受控
- 让 agent 能在测试、审查和验证反馈中逐步收敛
- 让 agent 按任务风险选择无人值守、被动观察、主动审批、人工纠偏或中断

## 方向二：持续运维智能体

持续运维方向关注：

- 部署和变更观察
- 服务巡检、健康、可用性、性能和容量
- 混合云资源治理、成本优化和自然语言问数适配
- 故障定位、恢复编排和恢复验证
- 低风险自动化与高风险变更审批

该方向与安全运营共享事件、资产、任务和审批基础设施，但不把稳定性故障和安全事件混成同一种领域对象。

## 方向三：安全评估与漏洞研究智能体

该方向面向明确授权的代码、依赖、配置、资产和隔离靶场，提供：

- 攻击面盘点和安全审计
- 授权渗透测试与攻击路径模拟
- 漏洞发现、复现、PoC 模拟验证和影响判定
- 修复复测、回归验证和证据报告

任何主动验证任务都必须有目标范围、授权主体、有效期、允许工具、速率限制、停止条件、隔离要求和 `SideEffectLedger`。不包含未授权扫描、开放式利用、跨边界扩张或自主 hack-back。

## 方向四：安全运营智能体

安全运营智能体是可以常驻运行的安全分析与处置系统。这类智能体应能够：

- 接受持续输入的安全相关日志或信号
- 对日志、流量和事件进行持续分析
- 关联资产、漏洞情报、后门、病毒、APT 和异常行为线索
- 生成调查假设、验证任务、事件和处置计划
- 按风险策略自动执行低风险动作，或请求人工批准高风险动作
- 调用安全评估与漏洞研究智能体进行受控验证
- 验证处置效果并沉淀规则、知识和复盘材料
- 允许用户随时通过聊天或控制面接入、查询、审批、暂停、恢复和接管

“对抗”在本项目中限定为检测、调查、验证、遏制、恢复和防护效果验证，不包含面向外部目标的自主反击。

## 共享的长期可恢复智能体运行时

四个方向都应支持多年生命周期，但长期运行属于共享 Harness 能力，不由某个领域自行发明。

运行时应将任务、状态、证据、授权、模型调用和副作用外化到可持久化记录中，支持：

- 交互、周期、事件驱动和常驻运营四种运行形态
- `Task / TaskRun / Attempt` 的心跳、租约、超时、重试、暂停、取消和恢复
- 进程、机器、网络、模型或版本变化后的检查点恢复
- 用户在任意时点加入已有运行上下文
- 授权过期、重新认证、预算、配额、背压和紧急停止
- 长期证据归档、压缩和可追溯查询

架构目标为 7x24 常驻和多年可恢复生命周期；Phase 1 只实现本地单机、顺序执行和可恢复检查点，分布式调度和高可用故障转移属于后续阶段。

## 共通架构原则

无论属于哪个专业方向，项目都应坚持以下共通原则：

- `safe`
- `steered`
- `auditable`
- `traceable`
- `human-steerable`
- `long-running`
- `feedback-driven`

这些原则对应的实际设计导向包括：

- 工具调用必须可控
- 权限边界必须清晰
- 执行环境应尽量受控或沙盒化
- 系统应支持多种人机介入模式：无人值守、被动观察、主动审批、人工暂停、恢复和接管
- 所有关键决策和执行动作都应可记录、可回放、可审查
- 长时任务必须支持状态延续，而不是依赖一次性上下文

## 通用能力与专用能力的分层思路

当前不直接定义最终目录结构，但应先明确分层思路。

更可能属于通用底座的能力：

- 任务编排与状态管理
- 长时运行任务的恢复、暂停与继续
- 工具调用控制
- 权限控制与策略约束
- 审批节点、人工介入模式与无人值守边界
- 统一日志、审计与 tracing
- 反馈循环与结果验证
- 上下文、记忆和中间状态沉淀
- 可观测性与回放能力

更可能属于软件开发方向的专用能力：

- 仓库与文件修改相关能力
- 构建、测试、lint、review、refactor 相关能力
- 开发任务拆解与回归验证

更可能属于安全领域方向的专用能力：

- 安全评估：攻击面、漏洞、PoC、渗透验证和修复复测
- 安全运营：安全信号、检测、调查、事件、处置和防护验证

更可能属于持续运维方向的专用能力：

- 服务健康、可用性、性能和容量输入
- 部署变更、资源、成本和故障流程
- 恢复编排与恢复后验证

总体原则是：

- 能抽象成稳定通用能力的，尽量下沉到通用层
- 明显依赖领域知识、输入类型或执行约束的，留在领域层
- 不为了“看起来优雅”而过度抽象

## 关于语言方向

当前考虑过的语言组合包括：

- Rust
- Python
- C
- Go

但语言分工目前还没有定稿。

当前更合理的原则不是先锁定语言，而是先明确职责边界，再决定语言是否适配该职责。也就是说：

- 先定义哪些能力必须稳定、长期运行、受控、可审计
- 再决定这些能力分别更适合用什么语言实现

因此，现阶段不应把语言选择写成架构承诺，只能视为候选技术栈。

## 当前明确不做的事

基于当前讨论，以下内容暂不在本文件中作为既定事实承诺：

- 不预先固定最终代码目录结构
- 不提前承诺插件体系的具体实现方式
- 不把任何行业场景写成公开定位
- 不把“未来愿景”写成“当前已实现能力”
- 不在当前阶段拆成多个独立项目
- 不把安全评估能力扩展为未授权攻击平台
- 不把安全运营的高风险处置设计成无需审批的自主反击

## 后续架构设计应优先回答的问题

后续如果进入具体架构设计，优先应该回答的问题包括：

- harness 的最小通用核心到底是什么
- GoalContract 如何定义目标、边界、成功标准、风险和验证契约
- LoopController 如何控制 observe / plan / act / verify / reflect / checkpoint / continue
- 长时任务的状态模型如何定义
- 无人值守、被动观察、主动审批、人工介入和接管模式如何定义
- tracing、审计和回放的数据模型如何定义
- 工具调用、权限边界和沙盒模型如何落地
- 四个专业方向分别通过什么接口接入共享 Harness
- 哪些能力必须共享，哪些能力必须隔离
- 如何验证 agent 没有跑偏，以及如何在跑偏后纠偏

## 当前方向总结

现阶段，`steerBox` 的方向可以概括为：

- 这是一个学习 Harness Engineering 的项目
- 项目保留一个统一核心，而不是拆成多个完全分离的学习项目
- 项目同时承载四个专业研发方向，并可在产品层投影为工程智能体和安全智能体两个产品族
- 核心关注点是长时执行、约束控制、反馈闭环、人类可掌舵运行模式、审计和 tracing
- 四个方向均以长期可恢复运行时为共同基础；长期在线不等于无限权限
- 架构上优先考虑“通用底座”和“领域专用能力”的清晰边界
- Goal、Loop、Efficiency、Plugin、Storage/Recovery 等横向能力作为支撑层，不替代四个专业方向
- 具体目录、语言和实现细节，留到后续架构设计阶段再收敛

这份文档应被视为后续架构设计讨论的方向指南，而不是最终设计稿。
