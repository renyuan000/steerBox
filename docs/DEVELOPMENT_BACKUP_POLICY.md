# 开发修改备份与清理约定

日期：2026-10-20。状态：用户已确认；自动备份、台账及清理工具尚未实现。

本约定用于保护开发者、主 Agent 和 subagent 的未提交成果，不等于 steerBox 运行时恢复能力，不扩大 Phase 1 范围。运行时快照另见 `WORKSPACE_SNAPSHOT_IMPLEMENTATION_PLAN.md`。

## 提交与保护分离

- 允许连续多轮修改不提交。一个独立功能点完成、审核及验证通过后，才精确提交；每个正式提交应可独立构建、部署和执行。
- 验证实际提交内容，不让验证依赖遗漏在工作区的文件。未执行的构建、部署或运行检查不得标为通过。
- 普通源码和 Markdown 基于最新内容精确 patch，不机械复制到临时目录再改回；风险修改前或必要阶段检查点保护未提交成果，不要求每次编辑都备份整文件。
- Git 已跟踪不代表未提交内容可从 HEAD 恢复。备份也不是并发锁：Agent 应分工文件，需隔离时用独立 worktree；共享文件发生变化后重新读取，不以旧副本覆盖。

## 存放与命名

约定根目录为 `/temp/codex/steerbox-backups/`，不放源码目录，不依赖 `/tmp/` 保存跨会话证据。本文未创建该目录，也未验证所在磁盘的崩溃持久性；不宣称可防磁盘损坏。

以下仅为布局示例，不是实际备份记录：

```text
steerbox-backups/
├── ledger.jsonl
└── 20261020-153000-a03-route-b007/
    ├── meta.json
    ├── tracked.patch
    └── new-files/       # 有需要保护的未跟踪新文件时才创建
```

目录名包含本地时间、Agent 短别名、任务短标签和备份编号。完整时区、会话 ID、路径和 commit ID 放元数据，不塞入文件名。编号在台账范围内唯一，创建时拒绝覆盖；`main` 表示主 Agent，`a03` 等别名须绑定真实会话 ID，不能因别名复用混淆归属。

## 记录字段

| 字段 | 内容 |
|---|---|
| `backup_id`、`schema_version` | 唯一编号、格式版本 |
| `created_at` | 带时区的创建时间 |
| `creator` | Agent 别名、名称、完整会话 ID |
| `task` | 任务 ID、任务摘要 |
| `repository`、`worktree`、`branch` | 实际工作现场；分离 HEAD 时如实记录 |
| `base_commit` | 创建时完整 HEAD；没有基准提交则不得伪造可恢复状态 |
| `files` | 相对路径、增删改类型、基准及备份内容校验值；不存在的文件明确标注 |
| `artifacts` | 补丁和新文件副本的路径、大小、校验值 |
| `content_provenance` | 内容来源；包含用户或他人修改时标记混合来源或未知 |
| `delivery_commits` | 实际交付提交完整 ID，可多个；创建时为空 |
| `review`、`verification` | 审核者、覆盖结论、验证对象、命令及结果；未做则明示 |
| `status`、`cleanup` | 状态、清理者、时间、精确删除范围及结果 |

备份创建者不等于全部内容的作者，subagent 自报完成不能替代主 Agent 验收。路径和任务描述也可能敏感，台账不自动进入模型上下文。

## 完整性与安全

- 已跟踪文件保存相对 `base_commit` 的整体差异，覆盖暂存及未暂存修改，支持二进制内容；需要恢复暂存边界时另记录暂存差异。
- 普通 diff 不包含未跟踪新文件，只按任务白名单另存；不顺带收集真实凭据、API key、endpoint、个人数据、运行配置或构建目录。确需特殊数据保护时先确定处理边界。
- 校验文件范围、制品完整性及可恢复性后才能标为有效保护。隔离恢复验证不得改写当前工作区；捕获期间发生并发变化时不得宣称一致快照。
- 目录和制品限制访问，不自动外传；文件权限不能隔离同一用户或 root。备份不能替代原子写入、并发协调或磁盘级备份。
- 不以 `git add` 充当多轮备份。普通 `stash push` 会改变现场；后续采用无打扰 Git 检查点时须验证新文件覆盖和引用保留，不暗中改变当前索引或工作区。

## 审核后自动清理

流程：保护成果 → 开发 → 审核与验证 → 精确提交 → 核验覆盖关系 → 清理对应备份。

机制实现后，下列条件全部满足才自动清理，无需重复询问：

1. 主 Agent 核验实际交付提交与备份、任务、文件的关联，不能只看提交时间或提交成功。
2. 逐文件核验备份内容已被实际交付提交无损覆盖；来源不清、混合来源或覆盖不完整的备份继续保留。舍弃内容不属于本自动清理授权。
3. 验证针对实际交付提交，不依赖未提交文件；记录对象、命令及结果。
4. 删除前重新核对身份、精确路径和校验值，确认仍是专用根目录内的该备份，不跟随被替换的符号链接或扩大删除到父目录。
5. 主 Agent 串行维护统一台账，先持久记录审核及交付关联，再清理，最后记录成功、部分失败或待检查；subagent 不并发改写台账。

删除补丁与新文件副本，台账保留必要元数据、归属、交付和清理证据，并简短报告范围与对应提交。失败、状态不明或已发现交付损坏时保留或标记待检查，不伪报成功，不机械沿用旧的通过结论。

不得清空其他备份、使用 `stash clear` 或为回收空间强制立即 prune；清理 stash 时核对对象 ID 和当时条目，不能只依赖会变化的序号。删除后不保证可恢复。
