# steerBox 开发审核约定

日期：2026-11-01。适用：项目开发及主 Agent 验收 subagent 成果；不是运行时 Code Review 服务，不新增后台人工审批。

## 官方参考及取舍

已阅读 Anthropic 于 2026-10-15 发布的《How the Claude Code team does code review》。文章介绍风险分工、多轮独立找错、独立验证和去重，并将高信号、避免重复评论作为目标。来源定位：`https://claude.dev/blog/solving-code-review-at-anthropic/`。标题和日期已按原文复核，不能从URL slug推断。

以下是针对本项目的工程选择，不是对官方产品实现或效果的承诺；文章中的内部质量数据不外推为 steerBox 的指标。

## 审核对象先固定

- 记录 task、仓库/工作树、base commit、候选 commit 或实际 diff，以及审核者。
- 未提交 diff 会变动；审查结论绑定读过的修订。作者修正后重审受影响路径，不能把旧 PASS 套到新逻辑。
- 人工或 Agent 的实现自审、独立规格审核、独立质量审核、主 Agent 验证分别记录，不互相冒充。

## 高信号审核

| 阶段 | 重点 | 交付 |
|---|---|---|
| 实现自审 | diff 是否越界、每处改动对应什么需求 | 实际文件及本地测试证据 |
| 规格审核 | 需求、状态迁移、失败/默认/边界是否符合契约 | 未满足项或有范围的 PASS |
| 质量审核 | 行为正确性、安全、资源限制、并发/恢复及性能 | 可触发的问题及其影响 |
| 主 Agent 验证 | 复核发现、回归、实际待提交树是否可构建 | 命令、退出结果和证据位置 |

- 按风险选检查视角，允许并行只读审查；有写入依赖的修复必须按文件分工或隔离，不让多个作者覆盖同一文件。
- 找错与判定分开。发现至少写明：对象修订、文件/行、触发条件、实际影响、证据和最小回归；没有复现的静态发现须给出完整控制流依据，不标为“已复现”。
- 必须核对 diff 外的相关调用者和不变量，不能只看新增行。既有问题明确标记来源，只有直接阻塞当前结果/验证/安全的才进入当前修复；其余按用户的周边修改门禁处理。
- 同一根因合并。优先处理会导致行为错误、安全事故、状态或数据损坏、失控发送及显著性能退化的缺陷；不把个人风格偏好包装成阻塞，不趁审核做无关重构。
- 独立反证最多三轮，找到足够证据或无新增风险即提前结束；这是本项目的成本上限，不要求每次跑满。不以无限加轮替代明确的测试。
- 没有新修订或新证据时，不重复跑整轮审核、反复输出相同发现。新修订先看增量，再根据影响决定是否扩展重审范围。
- 审核深度按改动风险决定，不因低风险改动机械追加人工询问；但Agent的审核不能充当用户规则或实际权限要求中的人工批准。达到轮数上限仍有阻塞时，重新检查根因和方案，不自动忽略缺陷或强行放行。

## 验证与交付

- bug 修复先有失败回归，再证明修复后通过。已有测试通过不能取代对新边界的验证。
- 主 Agent 必须检查 subagent 的实际 diff 和断言，再独立运行与风险相称的测试、编译及静态检查。审核者未跑测试就写“源码审查”，不写“测试通过”。
- 正式提交只包含同一独立功能及其直接文档/回归；实际提交应不依赖未提交文件而可构建。保留用户及其他 Agent 的无关改动。
- 验证产物留项目外持久目录，报告中区分 fixture、本地 transport、live provider 与部署验证；密钥和真实连接配置不进入审核上下文。
- 本文不自动配置任何外部 review 产品，也不修改全局 AGENTS.md、权限规则或运行时策略。运行时智能体可借鉴这些方法，但其自动审查、修复权限和预算仍需单独实现。
